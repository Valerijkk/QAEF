# Автоматизация тестов

## Принцип результата

При наличии write-authority `$qaef-write-*` сохраняет реальный тестовый код либо явно разрешённый test-support в целевом репозитории. Рекомендация, несохранённый snippet или общий список идей не равны выполненной задаче. Production-код не меняется: найденный дефект передаётся его владельцу отдельно.

## Выбор уровня

| Уровень | Проверяемая граница |
|---|---|
| Unit | Изолированное поведение небольшой единицы кода. |
| Contract | Совместимость опубликованного соглашения между сторонами. |
| API | Наблюдаемое поведение публичного интерфейса. |
| Integration | Граница с хранилищем, очередью, сервисом или иной зависимостью. |
| UI | Поведение компонента либо пользовательского потока. |
| Load | Поведение системы при оговорённом профиле нагрузки. |
| Security | Разрешённые негативные проверки защиты и авторизации. |

Уровень выбирают по риску, границе поведения и стоимости правдоподобного evidence, а не ради заранее заданного соотношения тестов.

## Сначала проверяемое поведение

До написания теста зафиксируйте требование, риск или TC — либо явно отсутствие связи — и ожидаемое наблюдаемое поведение. Сначала спроектируйте assertion и сценарий, затем минимальный код теста. Когда выбранный процесс допускает RED, используйте корректный RED; иначе покажите чувствительность assertion controlled mutation или negative sentinel. Не имитируйте failing baseline.

## Матрица сценариев

Для каждой задачи рассмотрите применимость следующих групп: happy, negative, authn, authz, boundary, edge, corner и failure-recovery. Выберите только относящиеся к риску варианты и кратко обоснуйте исключения. Например, отсутствие authz-проверки допустимо только если у проверяемой границы действительно нет авторизационного решения, а не потому, что сценарий неудобен.

## Качество теста

- Изоляция исключает скрытую зависимость от порядка, состояния других тестов и нерелевантных внешних систем в пределах выбранной архитектуры.
- Данные детерминированы: вход, предусловия и очистка либо их проектный эквивалент дают повторяемое наблюдение.
- Assertion проверяет существенный результат, а не только отсутствие ошибки, вызов мока или факт рендера без поведения.
- Название и структура позволяют сопоставить тест со сценарием и traceability.
- Повторное использование ограничено: helper извлекается, когда он убирает устойчивое дублирование без скрытия смысла сценария; преждевременная общая абстракция не создаётся.

В результат передаются изменённые пути, выбранные сценарии, traceability, evidence чувствительности, статусы `PASS`/`FAIL`/`UNKNOWN`/`NOT_RUN`/`BLOCKED`, остаточные риски и следующий шаг.

Оценка дизайна и независимая проверка описаны в [EVALUATION.md](EVALUATION.md).
