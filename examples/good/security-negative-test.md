# Принятый пример: разрешённая security-негативная проверка

## Запрос

> Режим `existing`. Проверить, что пользователь не может прочитать счёт другого пользователя. Разрешено изменить только существующий API-файл счетов; production-код не менять.

## Выбранный контекст

| Источник | Наблюдаемый факт | Решение, которое он поддерживает |
|---|---|---|
| `specs/invoices.md` | `GET /invoices/{id}` доступен только владельцу счёта; чужой счёт даёт `404`, чтобы не раскрывать факт существования. | Oracle: наблюдаемое отклонение и отсутствие disclosure. |
| `RISK-22` | Горизонтальное повышение привилегий на чтении счетов. | Связь с риском. |
| `tests/api/conftest.py` | Фикстуры `owner_client` и `other_client` выдают две разные подтверждённые тестовые личности. | Разрешённые данные и способ идентификации. |
| `tests/api/test_invoices.py` | Файл использует эти фикстуры; сценарии именуются по поведению. | Существующий стиль и сохраняемый путь. |

**Факты:** обе тестовые личности уже существуют в проекте; ожидаемый ответ на чужой счёт зафиксирован спецификацией.

**Вывод:** проверка выполняется внутри разрешённой границы приложения — это негативный сценарий авторизации, а не попытка обойти контроль доступа.

**Неизвестное:** подтверждённая команда запуска API-слоя не предоставлена.

## Сохранённый путь

- `tests/api/test_invoices.py`

Сохранённое изменение:

```python
def test_owner_reads_own_invoice(owner_client, invoice_of_owner) -> None:
    response = owner_client.get(f"/invoices/{invoice_of_owner.id}")

    assert response.status_code == 200
    assert response.json()["id"] == invoice_of_owner.id


def test_other_user_cannot_read_foreign_invoice(other_client, invoice_of_owner) -> None:
    response = other_client.get(f"/invoices/{invoice_of_owner.id}")

    assert response.status_code == 404
    assert str(invoice_of_owner.amount) not in response.text
```

## Evidence

- Статическое evidence: код сохранён в существующем API-файле; production-код не изменялся.
- Traceability: `specs/invoices.md` и `RISK-22` → два сценария: доступ владельца и отказ другому пользователю.
- Позитивный сценарий обязателен: без него `404` для чужого пользователя мог бы оказаться ложноположительным из-за недоступности ресурса вообще.
- Второе наблюдение во втором сценарии проверяет отсутствие disclosure — сумма счёта не должна попасть в тело ответа.
- Проверка остаётся в разрешённой границе: секреты не извлекаются, доступ не расширяется, production-настройки не меняются, нагрузка не создаётся.
- Чувствительность assertion не наблюдалась: controlled mutation не запускалась.

- Статус выполнения: `NOT_RUN`.

- Остаточный риск: сценарий покрывает одну границу одного эндпоинта. Он **не** доказывает отсутствие других уязвимостей и не заменяет security-обзор.
