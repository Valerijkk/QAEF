# Принятый пример: изменение integration-теста

## Запрос

> Режим `existing`. Проверить, что заказ, сохранённый в статусе `pending`, действительно читается из базы со своим статусом и не виден выборке оплаченных. Разрешено изменить только существующий integration-файл.

## Выбранный контекст

| Источник | Наблюдаемый факт | Решение, которое он поддерживает |
|---|---|---|
| `specs/orders.md` | Заказ создаётся в статусе `pending`; в выборку `paid` попадают только оплаченные. | Oracle и наблюдаемая граница. |
| `src/orders/repository.py` | Экспортируются `save_order(order)` и `list_paid_orders()`. | Граница репозитория. |
| `tests/integration/conftest.py` | Фикстура `db_session` создаёт транзакцию и откатывает её после теста. | Подтверждённая изоляция и владелец очистки. |
| `tests/integration/test_orders_repository.py` | Файл использует `db_session`, тесты именуются по поведению. | Существующий стиль и сохраняемый путь. |

**Факты:** изоляция уже решена проектной фикстурой; обе функции репозитория существуют.

**Вывод:** проверять нужно реальную границу с БД, а не mock этой границы — иначе тест не наблюдает то, ради чего написан.

**Неизвестное:** подтверждённая команда запуска integration-слоя не предоставлена.

## Сохранённый путь

- `tests/integration/test_orders_repository.py`

Сохранённое изменение:

```python
def test_pending_order_is_readable_and_excluded_from_paid(db_session) -> None:
    order = save_order(Order(customer_id=7, amount=200, status="pending"))

    stored = db_session.get(Order, order.id)
    assert stored.status == "pending"
    assert stored.amount == 200

    assert order.id not in [o.id for o in list_paid_orders()]
```

## Evidence

- Статическое evidence: код сохранён в существующем integration-файле, новый test-root не создавался.
- Граница выбрана реальная: используется настоящая сессия БД, а не подменённый репозиторий.
- Traceability: `specs/orders.md` → правило видимости `pending` → один сценарий с двумя наблюдениями.
- Assertions наблюдают сохранённый статус и отсутствие заказа в выборке оплаченных, а не факт вызова.
- Изоляция и очистка принадлежат проектной фикстуре `db_session`; собственный механизм очистки не вводился.
- Чувствительность assertion не наблюдалась: controlled mutation не запускалась.

## Честный статус

- Артефакт подготовлен: да; показаны сохраняемый путь и содержимое.
- Статус выполнения: `NOT_RUN`.
- Поведение целевой системы: `UNKNOWN` до наблюдаемой проверки.
- Остаточный риск: поведение при параллельных транзакциях этим сценарием не покрыто и остаётся `UNKNOWN`.
